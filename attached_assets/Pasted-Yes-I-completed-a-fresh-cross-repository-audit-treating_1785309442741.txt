🔴 P0 — Critical findings
1. Mutex's HTTP interceptor can leak the master token
This is one of the most serious frontend findings.
fetchInterceptor.ts decides whether a request is an API call using:
url.includes('/api/v1')
|| url.includes(cleanBase)
|| ...
But if restEndpoint is empty:
cleanBase = ''
and:
url.includes('')
is always true.
The interceptor can then add:
Authorization: Bearer <masterToken>
Content-Type: application/json
to arbitrary requests.
Why this matters
Imagine the app makes:
fetch("https://some-cdn.com/image.png")
while restEndpoint === ''.
The interceptor can treat it as an API request.
That is potentially:
Browser
 ↓
CDN / external service
 ↓
Authorization: Bearer MASTER_TOKEN
🚨 P0 security bug.
The API detection needs to require a non-empty, exact origin/base match.
🔴 2. Supabase login does not actually establish backend authorization for Mutex
The login page authenticates through Supabase, but after successful login it simply sets:
kanyoza_authenticated = true
and calls login().
The actual backend requests are then authenticated through:
masterToken
from the frontend store/localStorage.
So conceptually:
User A
   ↓
Supabase login
   ↓
UI access

BUT

API requests
   ↓
MASTER TOKEN
   ↓
backend
   ↓
ADMIN ACCESS
The backend actually supports Supabase JWT and workspace-specific API keys.
But Mutex isn't using that architecture for normal operator authorization.
Result
If several users can access Mutex and all use the same master token, they effectively share the same backend privilege level.
This defeats much of the backend RBAC/multi-tenant work.
Severity: 🔴 P0
🔴 3. Workspace creation is actually broken
This one is on the backend.
Mutex sends:
name
slug
plan
owner_email
for workspace creation.
But backend WorkspaceCreateRequest accepts:
name
id
description
instead.
Worse, backend then constructs:
Workspace(
    id=ws_id,
    name=body.name,
    description=body.description
)
while the actual Workspace model requires:
id
name
slug
and has no description field.
Result
Add Workspace is broken.
Severity: 🔴 P0
This is one of the places where the backend itself genuinely needs correction.
🔴 4. Posts API contract is still wrong
Mutex now sends:
caption
topic
category
state
platforms
scheduled_for
But backend's PostCreateRequest only accepts:
caption

category
state
And the backend's publish implementation does:
POST /posts

find all active brands
      ↓
first active brand
      ↓
trigger_for_brand()
So the frontend's:
selected brand
custom caption
selected platforms
scheduled time
are not being honored by this endpoint.
This is a real functional mismatch.
🔴 5. Schedule Later isn't implemented by /posts
Mutex sends scheduled_for.
Backend's PostCreateRequest doesn't accept it.
The publish branch immediately triggers the brand scheduler.
So:
Mutex:
Schedule for 18:00

Backend:
Trigger automation now
That is a P0 product correctness issue.
🔴 6. WorkflowRuns has a broken Trigger Run path
WorkflowRuns.tsx uses:
triggerPost()
from api.ts.
But forcePostNow() sends:
POST /bot/post
without brand_id.
The current backend explicitly requires:
brand_id
and returns 400 if it isn't supplied.
Therefore:
Workflow Runs → Trigger Run can fail every time.
The Scheduler page itself is better: it sends brand_id to /workflow/trigger.
This reveals an important issue:
Two frontend components are using two different generations of the API contract.
🔴 7. Users page isn't actually managing backend users
Users.tsx fetches /users initially.
But adding a user simply does:
setUsers(...)
locally.
Deleting a user does the same.
Toggling active/inactive does the same.
There is no backend mutation.
So:
Add User
   ↓
UI says "User added"
   ↓
refresh page
   ↓
User disappears
Severity: 🔴 P0
This page is currently a frontend mock/admin visualization, not a real user-management system.
🔴 8. Feature toggles contain fake controls
Features.tsx has:
Real:

POST /features/toggle
Fake/local:

Maintenance mode only modifies React state.
The "Save rate config" action is literally:
toast.success('Rate config saved')
with no backend request.
Quick actions also point to endpoints that aren't part of the current backend contract, including /system/cache/clear.
Severity: 🔴 P0/P1
🔴 9. API Manager's advanced key types aren't actually supported
Mutex allows:
Admin

But backend's APIKeyGenerateRequest accepts only:

Severity: 🔴 P1
🔴 10. Social-account credentials are still potentially exposed through platform_config
The backend deliberately strips:
access_token
encrypted_credential
from responses.
Good.
But platform credentials are moved into:
platform_config
and the response only removes the two top-level fields.
For example, Facebook credentials may be stored under:
platform_config.page_access_token
platform_config.verify_token
Those aren't stripped by the current response sanitization.
And Mutex's edit screen reads the returned account data.
Severity: 🔴 P0 security concern
The backend needs a recursive credential redaction layer, not just two .pop() calls.
🔴 11. Multi-tenant reads aren't consistently isolated
The backend correctly applies ownership checks to many resource-specific routes, e.g. brand jobs.
However, several global read endpoints don't scope data to the authenticated workspace:
GET /posts
GET /messages
GET /analytics
GET /analytics/performance
GET /analytics/posts-performance
GET /analytics/token-usage
For example, /posts reads the entire post_history table.
Likewise /messages gets recent messages globally.
This conflicts with the backend's own stated multi-tenant model.
Severity: 🔴 P0/P1
🔴 12. Supabase realtime subscriptions aren't workspace-filtered
Mutex subscribes to:
messages INSERT
posts INSERT
alerts INSERT
payloads INSERT
without workspace filters.
If the Supabase RLS policies don't strictly isolate these tables for the connected user, the browser can receive other tenants' events.
Even if RLS currently prevents it, this frontend design doesn't explicitly establish tenant context.
Severity: 🔴 P1

🟠 20. API Analytics contains fabricated historical data
This is particularly important for a system claiming enterprise analytics.
The chart does:
Math.random()
for historical API calls.
So the chart can visually show:

when most of those numbers aren't real.
Prometheus also derives P50/P99 from local latency history rather than backend percentile telemetry.
Production rule:
Never fabricate operational metrics.
If historical data isn't available:
No historical data
is better than an impressive-looking fake chart.
🟠 21. Incident Center generates synthetic incident timestamps
IncidentCenter uses:
Math.random()
to manufacture incident start times.
It also creates incidents from current health/log state rather than persistent incident records.
So it is currently an incident visualization, not a real incident-management system.
That's fine if labeled as such; not fine if presented as authoritative incident history.

🟠 23. Knowledge Base has an ownership hole on global deletion
Brand-scoped knowledge creation/list/search correctly uses:

But:
DELETE /knowledge/{knowledge_id}
doesn't perform the same ownership check before deletion.
That means the global deletion endpoint is weaker than the brand-specific endpoints.
Severity: 🟠 → potentially 🔴 depending on auth method
🟠 24. Global frontend polling is redundant with Socket.IO
The global Zustand store already receives:
stats
post_published
new_message
service_status
plugin_status
ai_provider_health
ai_decision
mission_status
via Socket.IO.
Yet it simultaneously runs:
/dashboard/live
/health/deep
every 120 seconds, plus enterprise polling every 60 seconds.
REST should be used primarily for:
initial hydration
reconciliation
recovery
rather than constantly competing with realtime state.
🟡 25. Event deduplication is global rather than event-type aware
Mutex has one global:
_seenEventIds
set.
That means if two different event categories happen to share the same ID, one can suppress the other.
Safer:
post:123
message:123
alert:123
job:123
rather than:
123
🟡 26. Scheduler has an initialization race
The Scheduler does:
fetchBrands()
    ↓
sets selectedBrandId
    ↓
fetchStatus()
inside one initial effect whose closure can still contain the old selectedBrandId.
So on first load:
No selected brand
    ↓
fetch brands
    ↓
select first brand
    ↓
fetchStatus() using old null
    ↓
brand jobs aren't loaded initially
The 15-second refresh eventually corrects it.
Not catastrophic, but it's a genuine race.
🟡 27. The frontend TypeScript configuration is too permissive
tsconfig.json does not enable:
strict
noUnusedLocals
noUnusedParameters
and allows JS.
For an application this large, strict TypeScript would catch a significant number of contract errors earlier.
🟡 28. PWA icons are external CDN URLs
The PWA manifest uses external Flaticon URLs.
For a production PWA, the icons should be packaged with the application.
Otherwise:
offline install
      ↓
external icon unavailable
      ↓
bad PWA metadata
Use local assets.
🟡 29. Auto-update PWA can reload the control console unexpectedly
registerType: 'autoUpdate' is convenient, but for an admin/automation console it can potentially update/reload while the operator is:
editing a post
changing scheduler settings
configuring credentials
investigating an incident
A controlled update prompt is safer for a mission-critical console.

🧩 The most important architectural conclusion
After this audit, I would not describe the system as:
"Frontend is broken and backend is finished."
That's too simplistic.
The real situation is:
                   KANYOZA PLATFORM
                         │
          ┌──────────────┴──────────────┐
          │                             │
      MUTEX                         BACKEND
   Control Plane                 Automation Core
          │                             │
          │       ┌─────────────────────┘
          │       │
          ▼       ▼
      API CONTRACT LAYER
             ⚠️
       inconsistent in places
There are three generations of frontend API usage currently coexisting:
Generation 1 — older helpers
api.ts
workflow/resume
logs/stream
logs/recent
logs/stats
etc.
Generation 2 — newer direct page integrations
Scheduler.tsx
brand_id
/workflow/trigger
BrandScheduler
Generation 3 — new JobService architecture
job_id
automation_jobs
BrandScheduler
JobService
Socket.IO
The frontend needs to be consolidated around Generation 3.
🎯 What should be fixed first
Phase 1 — Security / correctness
Fix fetchInterceptor token leakage.
Stop using a shared master token as the normal frontend authorization mechanism.
Fix nested social credential redaction.
Fix workspace creation.
Enforce workspace scoping on global reads.
Fix global Supabase realtime tenant filtering.
Phase 2 — Canonical API contract
Create one canonical frontend API layer around:
Workspace
Brand

It is making every existing feature tell the truth:

If UI says Scheduled     → actual persistent schedule exists
